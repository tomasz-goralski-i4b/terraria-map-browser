# ADR 0002 — Ship a generated Terraria map palette

- **Status:** Accepted (2026-10-07)
- **Affects:** M4 viewer (map colours), `packages/renderer`, the "No Terraria assets" hard rule in `AGENTS.md`

## Context

The renderer drew every block and wall in a hashed placeholder colour, so a world looked nothing like Terraria's
map. Terraria's map colours are a table inside the game: one colour per map option (most content has one, some
has several chosen by frame) for about 750 tiles and 370 walls, plus four liquids.

A proof of concept (draft PR #132) read that table at runtime from a local installation through reflection and let
the browser import the result as a JSON file. The reading part worked; the delivery did not. A visitor of the
deployed site would have to download and run a PowerShell script and then import a file before the map shows real
colours. That is a developer workflow, not a product.

The alternatives:

1. **Every user exports and imports the palette** (the POC). Needs Windows, the game and a script; most visitors
   never get the real colours.
2. **Average the colours of tile sprites** from the user's local textures (`packages/assets`). No game data is
   shipped, but the result is not Terraria's map palette (which is chosen per content, not averaged), and the user
   still has to connect their game folder.
3. **Ship the palette, generated by our own exporter from the game.** Every visitor sees the real map colours.

## Decision

Option 3. The repository ships `packages/renderer/src/palette/terraria-map-palette.generated.ts`, a TypeScript
module generated by `scripts/map-palette/export.ps1` from a local Terraria installation:

- **Generated, never hand-edited or copied.** The exporter loads the installed game in a 32-bit .NET Framework
  host, calls the game's own map initialization and reads the resulting colour tables by reflection. No decompiled
  code is read, and no table from TEdit, tModLoader or any other tool is copied; their documentation was used only
  to name the reflected members (see Sources).
- **A TypeScript module, not JSON or a binary blob.** It is type-checked like any other source, needs no parsing or
  validation in the browser, and a game update shows up as a readable diff (one line per content ID). At about
  29 KB (7.5 KB gzipped) a denser encoding is not worth it.
- **Data only.** The exception covers the RGB table and generated English content names described below: textures, sounds, fonts, worlds and
  game code remain forbidden. Sprites are still decoded only in the user's browser from their own installation.
- **Versioned.** The module records the game version it came from. After a game update, re-run the exporter and
  commit the regenerated module; `scripts/map-palette/export.test.mjs` covers the exporter on a synthetic assembly
  and, opt-in via `TERRARIA_ASSEMBLY`, against a real installation.
- **Content without a map colour** (IDs beyond the table, mod and unknown content) keeps its placeholder colour.

Rendering uses the observed frame rules described below, or the first map option without a rule. Lighting does not apply
(the game stores light per explored tile in its own map file, not in the world).

### Background and paint rules (2026-10-08)

The colour table alone does not say how the game picks the background by depth or how paint changes a colour.
These rules are **observed, not read**: `scripts/map-palette/observe.ps1` calls the game's map functions
(`MapHelper.CreateMapTile` for empty space in synthetic worlds with fractional surface and rock levels,
`MapHelper.GetMapTileXnaColor` for every tile and wall colour under every paint) and records only their results; the
rules in `packages/renderer` (`backgroundColor`, `paintedColor`) are our own description of those results, and
`scripts/map-palette/observe.test.mjs` compares them with a local installation (opt-in). The exporter also ships the
background colours (256-step sky gradient, dirt, rock, underworld) and the paint colours, like the content colours.
Shadow paint is approximated (the game's near-black grey is reproduced exactly for 83 % of colours, at most 5/255
off); everything else matches except six colour-paint results one step off from the game's floating-point
rounding. The world's surface and rock levels come from the world metadata, which the TypeScript codec now exposes.

## Addendum: map options by frame

Content with several map options picks one by its frame. The rule is observed, never read: `observe.ps1` places a
synthetic tile or wall with every frame of a grid (multiples of 18 and 22 on each axis) in a synthetic world, asks
`MapHelper.CreateMapTile` for its map colour index and maps it back to the option through the content's lookup range.
It repeats the samples at other positions and next to same-kind tiles; content whose option changes with anything but
one frame coordinate is listed as `dependsOnMore` and keeps option 0. For the rest, `export.ps1` writes
`tileOptions`/`wallOptions` (an axis and inclusive frame ranges per ID) into the generated module. The WebGL2 backend
resolves each block's option on the CPU at chunk upload, so GPU output stays equal to `renderChunk`.

## Addendum: English content names (2026-10-08, #184)

**User approval:** APPROVED by @tomasz-goralski-i4b on 2026-10-08, explicitly in the task conversation.
This approval covers the hard-rule/data-only exception for generated English content and paint names and their
runtime reflection/localization provenance. It does not constitute permission from Re-Logic or approval to merge.

The Content table becomes the editor's material picker. Palette keys such as `vanilla:1` cannot tell a user what
material they are choosing; the status bar and Inspector also need readable names. The generated module therefore
exports `terrariaMapNames`, typed as `MapContentNames`: English strings indexed by tile/wall ID and map option,
four liquid labels, paint names by paint ID, and the same game version as the colours. This extends the data-only
exception to these names;
it does not authorize shipping localization files, item inventories, textures or game code.

The exporter calls the installed game's `LanguageManager.SetLanguage("en-US")`, forces `ReloadLanguage`, initializes
the legacy name caches, calls `Lang.BuildMapAtlas`, and reads each option through `Lang.GetMapObjectName`. It uses
the game's own loader for embedded localization resources; those resources are neither parsed into a copied table
nor committed. Runtime observation of the unmodified 1.4.5.8 client and server showed that ordinary blocks, walls,
liquids and some object options have empty legend names. For example, tile 26 resolves to Demon Altar and Crimson
Altar, but tiles 0 and 1 and walls 1 and 2 have empty names. Restricting the source to the map legend would leave
ordinary building materials unnamed.

Following the user's request to also investigate item reflection and localization assets, unnamed entries may use
the resolved `Item.Name` of items whose runtime `Item.SetDefaults` metadata places that exact `createTile` or
`createWall` ID. A name is used only if **all** placement items for the ID agree on a single distinct name; ambiguous
IDs remain unnamed. No item-name table is shipped. A synthetic local player lets cosmetic item initialization run
without loading a player or graphics. Any failed item initialization aborts export rather than silently losing
candidates. Names retain their exact game wording: Dirt Block (tile 0), Stone Block (tile 1), Stone Wall (wall 1),
Natural Dirt Wall (wall 2), and Dirt Wall (wall 16). This is a material-name fallback, not a claim that the map
legend displays those names or that an item placement style is the same as a map option.

Further runtime investigation on 2026-10-08 found `TileID.Grass = 2` and `TileID.Plants = 3`, but these are
symbolic identifiers, not localized material labels. The loaded English dictionary contains exact "Grass" and
"Plants" values only under `RandomWorldName_Noun`, not corresponding `MapObject`, `TileName` or `WallName` keys.
World-name nouns do not establish a tile-label mapping. Grass placement candidates include Grass Seeds, Staff of
Regrowth and Axe of Regrowth; plants have several flower and grass seed names. Both therefore deliberately retain
`vanilla:2`/`vanilla:3`. A future symbolic-ID fallback would need a separate naming policy and casing rules;
this exporter does not infer material labels from unrelated localization keys.

Liquid labels are resolved through the game's localization keys `LegacyInterface.53`, `LegacyInterface.56`,
`LegacyInterface.58` and `SlimeNames_Rainbow.Shimmer`. Runtime observation confirmed Water, Lava, Honey and Shimmer;
the last key is a shared English label rather than a map-legend entry. Missing or unresolved keys abort export.
These four key references are part of the exporter contract; the strings themselves always come from the game.

Paint names use the same item scan: `Item.paint` supplies the paint ID and `Item.Name` supplies the English name,
again only when candidates agree. Runtime observation resolves paint 19 to Deep Cyan Paint, 29 to Shadow Paint,
and 30 to Negative Paint. The palette also includes paint ID 31, which has no current paint item and keeps
an empty name. Status descriptions append a nonzero block/wall paint name to its material; Inspector paint fields
show both name and ID. Unknown paint IDs keep a `paint:N` key. This addition follows the user's paint-name request.

The UI selects a block option only when the observed rule's frame axis is known. Otherwise it uses option zero.
An unnamed option falls back to the option-zero name, then the palette key. Wall names use option zero because
the CWM does not store wall frames. Unknown/mod references keep their keys. Content rows show option-zero names,
filter on names, keys and kind labels (including unknown/mod walls), and retain keys in the ID column, hidden by default.

The generated name section is about 36 KB (9 KB gzipped) for 1.4.5.8, with names for 660 tile IDs, 282 wall IDs and
30 paint IDs. The fixture exporter covers single and multiple options in both layers, initialization order,
ambiguous placements, escaped strings, and unsupported contracts.
The normal TypeScript build checks the generated module; the local-installation test compares representative
names and dimensions with the exported colour table. Re-run the exporter after game updates.

## Rights

The shipped data consists of colour values and short English material labels, rather than artwork or complete
localization assets. Fan tools have published Terraria's map colour tables for years without objection. This is a
judgement, not legal advice, and it is not permission from Re-Logic. If the
rights holder objects, the module is removed and the renderer falls back to placeholder colours (it already does
for anything missing from the table), so nothing else depends on its presence.

## Sources

Used to name the reflected members (`MapHelper.Initialize`, `colorLookup`, `tileLookup`/`tileOptionCounts`,
`wallLookup`/`wallOptionCounts`, `liquidPosition`); no code or colour values were taken from them:

- [tModLoader `MapHelper` API](https://docs.tmodloader.net/docs/stable/class_map_helper.html): initialization and
  the tile/wall lookup arrays with their option counts.
- [TEdit `MapColorsExporter.cs`](https://github.com/TEdit/Terraria-Map-Editor/blob/99928583086ff1c0c970c5528c7d72c76da39a53/src/SettingsFileUpdater/TerrariaHost/MapColorsExporter.cs#L75-L94),
  revision `99928583086ff1c0c970c5528c7d72c76da39a53`, lines 75–94: names and static nature of the palette fields.
- Terraria 1.4.5.8, by runtime reflection only: the Windows assembly needs a 32-bit .NET Framework host and the
  launcher's save root, and the four liquid colours follow each other at `liquidPosition`.

## Consequences

- `AGENTS.md` keeps the "No Terraria assets" rule and names the colour and English-name exports as its data-only exception.
- The renderer API takes an optional `mapPalette` (`renderChunk` options, `createMapRenderer` options); without one
  it draws placeholders, which keeps renderer tests independent of game data. The web app passes the shipped one.
- The POC's browser import (file input, origin storage) is dropped. A user-supplied palette, for example for a mod,
  can be revisited once there is a concrete need.
